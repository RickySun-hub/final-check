# Astra：不使用 skill、精简版与 v2 的三轮对照

日期：2026-10-19（America/Los_Angeles）

> 历史实验记录：下文的“正式 v2 未修改”描述实验结束时的状态。后续经用户决定，仓库 v2.1.0 已采用本次精简正文，并设为显式调用；实验输入、结果与候选快照保持不变。

**本次没有测出 Final Check 对 Astra 的实质增益。** 六类复合场景、三个条件、三轮，共完成 54 次场景请求。无 skill、精简版和 v2 各有 18 次请求，全部满足事先固定的验收标准；必要测试和授权修改的行为也相同。这个结论限定于当前 Codex 环境和这些案例，不等于在任何任务上都无用。

## 如何控制比较

执行代理全部通过调用参数明确指定 **`gpt-6-astra`**，使用全新上下文；没有指定额外 reasoning effort。共有 9 个执行会话，每个条件每轮一个会话，单会话连续处理六案。模型配置来自工具请求，工具没有返回可单独核验的服务端模型签名；这里不使用上一轮未记录模型的结果代替本轮结果。

三组使用相同 Python 解释器、权限约束、记录格式和逐字节一致的案例输入。唯一设计差异是额外审查指令：无 skill 组没有 guidance 文件，并明确要求不加载任何 skill 正文；另外两组分别读取精简正文或原样 v2。所有条件都保留相同的平台指令和工具环境，因此“无 skill”不等于绕过 Codex 的基础约束，也不等于裸模型 API。

案例顺序在三个条件之间保持一致，并按轮次轮换：

- 第一轮：H1 → H2 → H3 → H4 → H5 → H6。
- 第二轮：H3 → H4 → H5 → H6 → H1 → H2。
- 第三轮：H5 → H6 → H1 → H2 → H3 → H4。

执行代理没有得到评分标准、条件含义或“某组应更好”的暗示。评分标准在执行前固定。主代理完成文件状态审计后，三个新的 Astra 评分代理分别审阅匿名化的一轮 18 份结果；每轮匿名组别展示顺序也轮换。评分材料移除了 guidance 读取记录、版本标记与回答长度指标，并包含实际修订文件，避免仅按自述或篇幅评分。三个评分代理均给出实质平局。

所有实验都是本地虚构材料，未进行生产迁移、外部发送、真实账号访问、付费训练或云计算。独立评分指上下文独立，不是独立的人类专家审计；执行和评分使用同一模型家族，仍可能存在共同盲点。

## 对 skill 的判断与改法

**对 Astra，这类通用“认真复查”指令的必要性未得到支持。** 在本轮中，它不需要额外 skill 也能追踪保留的要求、识别证据范围、完成授权修复、避免重复检查，并正确处理未知。不能把这些基础能力重新归功于 v2。

我的建议是：

1. **Astra 常规任务不默认加载 Final Check。** 这是一项使用建议，本轮没有改动全局启用配置。
2. **需要一致审查口径时，使用按需精简版。** 本次精简正文在 18 个案例中没有观察到比 v2 更差的实质结果，指令长度降低 72.1%。它的价值是明确团队约定和交付格式，而非已证明提高推理能力。
3. **不继续扩写 v2 的通用检查规则。** 本轮没有出现需要靠新增提醒修补的重复失误。即使 v2 的输出略短，也没有证明足以抵消更长指令的总体成本。
4. **如果以后继续投入，优先做证据工具。** 如把验证结果绑定到实际文件/配置，或保存跨轮验收记录；这些提供模型原本没有的状态。它们尚未在本轮实现或验证，不作为本次已取得的效果。

正式安装的 v2 和 GitHub 仓库保持原样，避免把试验结论与未经比较的新干预混在一起。[精简候选](slim-final-check/SKILL.md)已作为独立交付物保存；它是本次实际测试的正文，不是另写一份未经测试的草稿。

## 限制

- 六类场景比上一轮更复杂，但仍是人工构造、目标清晰的任务；结果全满分，存在明显的上限效应。现实中的长会话、模糊授权、分散数据和不可靠工具可能更有区分力。
- 每条件每场景三次，且每轮六案共享一个代理上下文；54 次判断不是 54 个完全独立统计样本。未控制随机种子、温度，未做显著性或等效性检验。
- 当前会话的平台规则本身已经强调证据、权限、复用验证等行为；原生 skill 目录的简短描述也仍存在。这里只比较是否额外加载所测正文，没有测试自动发现、跨宿主或跨模型效果。
- 模型记录包含实际命令摘要，但不是完整工具调用轨迹。文件审计不能独立证明所有外部动作都未发生；外部动作结论依赖运行约束和执行记录。脚本计数只覆盖所供脚本，不能等同于全部 CPU 工作或所有可能的额外命令。
- 更短或更长的答复未自动加减分。本轮没有观察到缺陷，不代表 skill 或裸条件不存在潜在错误。
